# 快速启动+ 模式下的开机唤醒：探索记录

> 记录时间：2026-10-14 ｜ 电视：LG OLED55G6PCA（G6，webOS 26，开发者模式）｜ 电视 IP：192.168.1.4:9922
> 目标：在「快速启动+」开启、开机直接进 HDMI4（不是首页）的情况下，遥控关机后短时间内遥控开机，仍能自动发送 WOL 魔术包唤醒电脑。

## 1. 需求与两个场景

| 场景 | 电视设置 | 开机表现 | 触发来源 |
|---|---|---|---|
| A（早期已实现） | 快速启动关闭 | 冷启动进首页 | ActivityManager persist activity 在冷启动时回调服务 |
| B（本次实现） | 快速启动+ 开启 | 从 ActiveStandby 快速恢复，进 HDMI4 | tvpowerd 的 preparePowerOn 订阅通知 |

## 2. 为什么旧方案在场景 B 完全失效

1. **快速启动+ 不是重启**。关机进入 ActiveStandby，系统不重新引导；persist activity 只在冷启动时重新执行，所以场景 B 里 `wake` 回调根本不会发生。
2. **开机后前台是 HDMI4**，我们的 Web 应用不在前台，前端 JS 没有任何执行机会。
3. **JS 服务是按需拉起、空闲自动退出的**。电视上 `/lib/node_modules/webos-service/lib/activitymanager.js` 里 `idleTimer` 默认 5 秒，`_activities` 为空就 `process.exit(0)`（日志：`no active activities, exiting`）。也就是说，即使向系统注册了"开机通知"，服务进程早已退出、总线连接断开、订阅被回收，通知永远不会到达。

结论：**必须先让服务常驻，再订阅系统的开机事件。**

## 3. 官方文档能查到什么（C:\0_Code\webos-docs-zh）

- 全部文档里出现过的 luna 服务只有：`blegatt`、`camera`、`connectionmanager`、`drm`、`keymanager3`、`mrcu`、`sm`、`tv.systemproperty`。
- **没有任何"电源状态 / 开机事件"API**。`tv.systemproperty/getSystemInfo` 只有 boardType、modelName、firmwareVersion 等静态信息。
- ActivityManager 文档里的 `type.persist` / `type.power` / `powerDebounce` 都**不提供"从待机恢复"的触发**。
- 结论：官方文档到此为止，必须实机探测系统内部的 luna 服务。

## 4. 实机探测方法（可复用）

### 4.1 连上电视：本地 TCP 中继绕开 VPN

公司 SecoClient 会不断抢注 `192.168.1.0/24` 路由，直连 192.168.1.4 会走到 VPN 网卡。做法见 `deploy-wakeonlan.ps1`：起一个只监听 `127.0.0.1` 的中继，由它**绑定本地物理网卡 IP（192.168.1.6）**去连电视，并把 ares 设备配置临时指向中继。Windows 在 socket 绑源地址时会强制走该网卡，从而绕开路由表。

### 4.2 在电视上执行命令

- `ares-shell` 在 `tv` profile 下直接报 `This command is not supported by current profile`，**不能用**；用 `ares-novacom --device lg --run "<命令>"`。
- 复杂命令（含引号、管道、`$`）用 base64 绕过各层引号解析：

```powershell
$script = Get-Content .\probe.sh -Raw
$b64 = [Convert]::ToBase64String([Text.Encoding]::UTF8.GetBytes($script))
ares-novacom --device lg --run "echo $b64 | base64 -d | sh"
```

- 普通用户不能执行 `/usr/bin/luna-send`（root only），用 `/usr/bin/luna-send-pub`。
- **`luna-send-pub` 一定要加 `< /dev/null`**。它是从 stdin 读 payload 的，脚本通过管道喂给 `sh` 时，它会把剩下的脚本吃光，表现为"命令执行了但完全没有输出"。

### 4.3 值得翻的现场

| 路径 | 用途 |
|---|---|
| `/tmp/var/log/legacy-log` | 各 JS 服务 `console.log` 的输出（`/var/log` 是它的软链） |
| `/tmp/var/log/dbg-log` | tvpowerd、surfacemanager 等原生服务的启动期日志 |
| `/usr/share/luna-service2/api-permissions.d/*.api.json` | **最关键**：某个 luna 方法的权限分组（public / tv.management / private / all…） |
| `/usr/share/luna-service2/services.d/*.service` | 服务名 → 可执行文件 |
| `/usr/share/luna-service2/roles.d/*.role.json`、`client-permissions.d/*.perm.json` | 角色与客户端权限 |
| `/lib/node_modules/webos-service/lib/*.js` | JS 服务运行时源码（进程存活、订阅、activity 逻辑） |
| `/proc/<pid>/cmdline` | 找 tvpowerd 等常驻进程（`/usr/sbin/tvpowerd` 在 jail 里看不到，但进程在跑） |

## 5. 核心发现：`com.webos.service.tvpower`

### 5.1 权限

`api-permissions.d/com.webos.service.tvpower.api.json` 的 `public` 分组里有：

```
com.webos.service.tvpower/power/registerPreparePowerOn
com.webos.service.tvpower/power/responsePreparePowerOn
com.webos.service.tvpower/power/registerPrepareResume
com.webos.service.tvpower/power/responsePrepareResume
com.webos.service.tvpower/power/registerPreparePowerOff
com.webos.service.tvpower/power/registerPrepareActiveStandby
...
```

而 `getPowerState`、`powerOff`、`registerPreparePowerOn` 的 `power2/*` 版本只出现在 `tv.management` / `private` / `all` 分组里 → 普通应用调用会被拒：

```
{"errorCode":-1,"returnValue":false,"errorText":"Denied method call \"getPowerState\" for category \"/power\""}
```

所以**只能注册、不能查询电源状态**，方案必须事件驱动。

### 5.2 注册（订阅）

```
luna-send-pub -i -f luna://com.webos.service.tvpower/power/registerPreparePowerOn \
  '{"clientName":"com.woltv.wakeonlan.service","subscribe":true}' < /dev/null
→ {"subscribed":true,"returnValue":true}
```

要点：
- 用的是 **`power`（v1）路径**，不是 `power2`（power2 对普通应用 Denied）。
- `clientName` 是必填参数（缺了报 `-5 'clientName' is needed`），显式写服务名。
- 同一个 clientName 重复注册会返回 `-3 The client is already registered`。

### 5.3 通知与应答

电视开机时，tvpowerd 会**在这条订阅上推送事件**，实测收到的负载：

```json
{"returnValue":true,"timestamp":"3367540976","onOff":"on",
 "reason":"remoteKey","state":"Active Standby","instantBoot":"on"}
```

`state: Active Standby` + `instantBoot: on` 正好就是"快速启动+"场景。

收到后必须应答，否则 tvpowerd 一直等：

```
luna-send-pub -n 1 -f luna://com.webos.service.tvpower/power/responsePreparePowerOn \
  '{"clientName":"...","ack":true,"timestamp":"3367540976"}' < /dev/null
```

参数校验顺序（一步一步试出来的）：

| 发送内容 | 返回 |
|---|---|
| `{clientName}` | `-11 'ack' is needed, invalid param` |
| `{clientName, ack:1}` 或 `ack:"true"` | `-11 'ack' is needed`（只接受布尔 true） |
| `{clientName, ack:true}` | `-12 'timestamp' is needed, invalid param` |
| `{clientName, ack:true, timestamp:"<事件timestamp>"}` | 参数通过；过期时报 `-13 The response is too late` |

`timestamp` 必须原样回传事件里的那个值，应答窗口很短。

## 6. webos-service 运行时行为（决定架构）

来自电视上的 `/lib/node_modules/webos-service/lib/`：

- `activitymanager.js`：`idleTimeout` 默认 5 秒；`_add()` 会 `_stopTimer()`，`_remove()` 在 `_activities` 清空后 `_startTimer()`，超时即 `process.exit(0)`。
- `ActivityManager.create('名字', cb)`（传字符串）→ `_createInternal()`：只创建 JS 侧占位 activity 并把它塞进 `_activities`，从而**永久停掉 idle 计时器**。这是让 JS 服务常驻的最省事办法。
- `service.js` 的 `_dispatch()` 会给每个请求创建一个内部 activity，响应后 complete；只要还有别的 activity 存活，就不会退出（日志里反复出现 `idle timer already stopped, ignoring` 即为常驻生效）。
- `subscription.js`：`payload.subscribed === false` 时会自动 cancel 并触发 `cancel` 事件，适合做断线重连。

## 7. 最终架构

```
电视开机（冷启动 / 快速启动+恢复）
        │
        ├─ 冷启动：persist activity → luna://…/wake (params.reason=boot)
        │
        └─ 快速启动+：tvpowerd 在 registerPreparePowerOn 订阅上推事件
                          │
                          ▼
        常驻服务收到事件 → 立刻回 responsePreparePowerOn{ack,timestamp}
                          │
                          ▼
        等 connectionmanager 报告 connected → 发送 1 次魔术包
```

兜底与保护：

- **时钟跳变兜底**：10 秒心跳，若两次间隔 > 60 秒，判定为"刚从待机恢复"，同样触发发送（防订阅丢失/进程被冻结）。
- **30 秒去重**：避免事件通知与兜底重复触发。
- **60 秒重注册**：注册状态不是 subscribed 时自动重订阅；订阅 cancel 后 5 秒重试。
- 保留冷启动 persist activity，场景 A 行为不变。

## 9. 验证证据（实测日志）

```
power event registerPreparePowerOn: {"returnValue":true,"timestamp":"3367540976",
  "onOff":"on","reason":"remoteKey","state":"Active Standby","instantBoot":"on"}
power trigger: powerOn detail={...}
magic packet attempt 1/3 reason=powerOn ok=true
magic packet attempt 2/3 reason=powerOn ok=true
magic packet attempt 3/3 reason=powerOn ok=true
```

> 上面是当时的原始日志：首次打通时为了排除"网络还没就绪"，实现成连发 3 次。功能确认可用后已简化为**只发 1 次**（日志变为 `magic packet sent reason=powerOn ok=true`），本节记录保持原样。

当时应答调用还没补齐参数，日志里是：

```
ack responsePreparePowerOn for registerPreparePowerOn:
  {"returnValue":false,"errorCode":"-11","errorText":"'ack' is needed, invalid param"}
```

据此在 §5.3 逐项试出完整参数（`ack` + `timestamp`），代码已修正并重新部署；**这一点只做过参数合法性验证，尚未再走一次真机开机复测**。它不影响唤醒本身（魔术包已发出且电脑被唤醒），只影响对 tvpowerd 的应答完整性。

`getStatus` 里可读的关键字段：

- `resident.ok` / `resident.activityId` —— 服务是否常驻
- `power.triggers.registerPreparePowerOn.subscribed` —— 是否成功注册开机通知
- `power.eventCount` / `power.lastEvent` / `power.events` —— 收到的开机事件与发送结果
- `heartbeat.gapCount` —— 兜底触发过几次
- `startedAt` / `uptimeSec` —— 服务实例存活时长（跨待机不重启说明常驻有效）

## 11. 坑与注意

1. `power2/*` 对普通应用全部 Denied，只能用 v1 `power/*`；`getPowerState` 永远拿不到，不要试图轮询电源状态。
2. `luna-send-pub` 记得 `< /dev/null`；`luna-send` 只有 root 能跑。
3. `ares-shell` 不支持 tv profile，用 `ares-novacom --run`；命令复杂就 base64 包一层。
4. 服务常驻会占内存，不要在里面做秒级轮询——本项目只在事件和 10 秒心跳上工作。
5. 应用界面里不放功能开关，功能全部写死（项目约定）。
6. 电视系统升级或换机后，tvpower 的内部 API 可能变化：先跑第 2 步看 `subscribed` 是否为 true，再看第 4 步日志里有没有 `power event`。
7. 界面显示的 `buildHash` 表示电视上当前运行的是哪个提交；只改文档不重新打包时，它仍指向最后一次部署的代码提交。
